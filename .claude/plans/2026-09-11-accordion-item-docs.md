## Context — the three facts that decide this plan

**1. Stencil writes one `readme.md` per DIRECTORY, not per component.**
`getDocsComponents` computes `readmePath` as `join(dirname(sourceFilePath), "readme.md")`
(`node_modules/@stencil/core/compiler/stencil.js:275446`) and `generateReadme`
writes to exactly that path for every component (`:276330-276357`). The
`docs-readme` target's `dir` option only relocates the tree by
`relative(config.srcDir, readmePath)` (`:276337-276338`) — it does not
disambiguate two components sharing a directory. Two components in one directory
means the second write wins.

```derived
$ for f in mud-accordion mud-breadcrumb mud-header mud-menu mud-sidebar mud-tabs; do echo "$f -> $(head -1 src/components/$f/readme.md)"; done
mud-accordion -> # mud-accordion-item
mud-breadcrumb -> # mud-breadcrumb-item
mud-header -> # mud-header-services-menu
mud-menu -> # mud-menu-item
mud-sidebar -> # mud-sidebar-item
mud-tabs -> # mud-tabs
```

Five of six grouped directories document the wrong component today. This plan
fixes the Accordion row only.

**2. The audit tooling resolves a component strictly by directory.**
`resolveComponentPaths` (`scripts/audit/lib/component-paths.mjs:70-98`) probes
`src/components/<tag>/` then `src/hidden/<tag>/` and returns `found: false`
otherwise. No directory, no component:

```derived
$ node scripts/audit/05-story-exports.mjs mud-accordion-item --json | python3 -c "import json,sys;d=json.load(sys.stdin);print(json.dumps({'summary':d['summary'],'findings':[f['code'] for f in d['findings']]}))"
{"summary": {"errors": 1, "warnings": 0, "info": 0}, "findings": ["STRUCTURE-NOT-FOUND"]}
```

**3. `web-component-analyzer` reads JSDoc tags, not Stencil decorators.**
Storybook's web-components ArgTypes extractor groups manifest data into
`properties`, `attributes`, `events`, `slots`, `css custom properties` and
`css shadow parts` (`node_modules/@storybook/web-components/dist/entry-preview-argtypes.js`,
`extractArgTypesFromElements`). The manifest feeding it comes from `wca`, and `wca`
takes its events from `@fires`, its parts from `@csspart`
(`parseJsDocForNode(node, ["csspart"], …)` in
`node_modules/web-component-analyzer/lib/cjs/chunk-transform-analyzer-result-jzWAvD19.js:1675`)
and its slots from `@slot` — never from `@Event()` or Stencil's `@part`. The item's
docblock carries `@slot` ×5 and `@part` ×2 and a single `@fires mudToggle`, so the
manifest today has no parts and only one of the two events:

```derived
$ node -e "const t=require('./.storybook/custom-elements.json').tags.find(t=>t.name==='mud-accordion-item');console.log('events:',JSON.stringify((t.events||[]).map(e=>e.name)),'cssParts:',JSON.stringify(t.cssParts))"
events: ["mudToggle"] cssParts: undefined
```

Falsified directly, rather than reasoned: a copy of the source with `@csspart` ×2
and `@fires mudAccordionItemKey` added to the docblock, analyzed on its own.

```derived
$ npx wca analyze <scratch>/probe-item.tsx --format json --outFile <scratch>/probe3.json && node -e "const t=require('<scratch>/probe3.json').tags[0];console.log('events:',…,'cssParts:',…)"
events: ["mudAccordionItemKey","mudToggle"]
cssParts: ["header","panel"]
```

Two consequences the bar depends on. First, joining the `@Event` decorator and its
property onto one line changes nothing — tested and refuted before the docblock
hypothesis was reached, so the fix is a docblock edit and never a code reformat.
Second, `properties` also carries `host`, `mudToggle` and `mudAccordionItemKey`,
because `wca` lists every public class field. The two emitters do not surface twice:
`extractArgTypesFromElements` spreads `events` AFTER `properties`, so a name in both
resolves to its event row. `host` has no such twin and is a genuine spurious prop —
present on every component in this repo today, suppressed here for the two Accordion
metas only.

Stencil 4.43.4 ships a `docs-custom-elements-manifest` output target that emits
CEM 2.1.0 with `cssParts` derived from `@part`, plus `attributes` and `members`
(`stencil.js:275800-275850`), and Storybook accepts that shape
(`isValidMetaData` accepts `modules[]`). Switching to it would fix parts,
attributes and methods for every component at once — and change every component's
docs page at once. Rejected here as out of scope; recorded as a follow-up.

two `git mv`s and leaves C available as a follow-up per directory.

## Acceptance bar

Zero-tolerance:

1. `node scripts/audit/05-story-exports.mjs mud-accordion-item --json` returns
   `summary.errors == 0` and no `STRUCTURE-NOT-FOUND`.
1b. `node scripts/audit/01-component-structure.mjs mud-accordion-item --json`
   returns `summary.errors == 0`. This is a separate bar because it is a separate
   script: `STRUCTURE-MISSING-TOKENS`, which the tolerance list below names, is
   emitted only by `01` (`grep -rln STRUCTURE-MISSING-TOKENS scripts/audit/*.mjs`
   → one file), never by `05`.
2. On the BUILT Storybook, the Accordion docs page renders an ArgTypes table for
   `mud-accordion-item` alongside `mud-accordion`, covering the member set below —
   the denominator, derived from the source rather than asserted:

   ```derived
   $ python3 -c "import re;s=open('src/components/mud-accordion/mud-accordion-item.tsx').read();print('props',re.findall(r'@Prop\([^)]*\)\s+(\w+)',s));print('events',re.findall(r'eventName:\s*.(\w+)',s));print('slots',re.findall(r'@slot\s*(\S*)\s*-',s));print('parts',re.findall(r'@part\s+(\S+)\s+-',s))"
   props ['open', 'disabled', 'heading', 'supportingText', 'itemId', 'appearance', 'breakpoint', 'size', 'iconPosition']
   events ['mudToggle', 'mudAccordionItemKey']
   slots ['heading', 'supporting', 'icon-start', 'trailing', '']
   parts ['header', 'panel']
   ```

   9 props + 2 events + 4 slots + 2 parts = **17 rows**. Two documented
   subtractions, both properties of the extractor rather than of this change:

   - the **default slot** cannot render. `mapData` filters `item => item && item.name`
     (`node_modules/@storybook/web-components/dist/entry-preview-argtypes.js:49`) and
     `wca` emits the default slot with `name: ""`, which is falsy. 5 declared slots,
     4 renderable.
   - the two `@Method()` members never reach the table because `wca`'s experimental
     v1 output emits no member for them at all — the tag's `properties` array is
     exactly `[open, disabled, heading, supportingText, itemId, appearance,
     breakpoint, size, iconPosition, host, mudToggle, mudAccordionItemKey]` and there
     is no `methods` key for the extractor to read. (The extractor does carry an
     `item.kind === "method"` early return, but nothing in this manifest reaches it.)
     `setOpen` and `focusHeader` stay documented in the generated `readme.md`.

   The **`mud-accordion-item` rows** must come from the generated manifest, not from
   hand-authored `argTypes`: a table filled by hand satisfies the letter of this bar
   while defeating its purpose, so Phase 4 Step 3 checks that each item row's
   description text matches the JSDoc in the source, and the item stories file this
   plan writes declares no `description` in any `argTypes` entry.

   The clause is scoped to the item's rows deliberately. The container's own stories
   file hand-authors four descriptions today
   (`mud-accordion.stories.ts:435-455`: `mode`, `appearance`, `breakpoint`, `label`),
   which is pre-existing committed behaviour on this branch's base. Deleting them is
   a defensible follow-up and is not this PR's scope; a bar phrased over the whole
   page would grade non-PASS on arrival, before a single line of this plan runs.
3. `head -1 src/components/mud-accordion/readme.md` is `# mud-accordion`, and
   `src/components/mud-accordion-item/readme.md` exists with H1
   `# mud-accordion-item`.
4. `yarn test --project spec` green AND its `Tests N passed` count equal to the
   count recorded before Phase 1. Green alone is not this bar: a spec file that
   never registers with vitest is green and empty.
5. `node scripts/audit/12-console-errors.mjs mud-accordion --json --port 6099` and
   the same for `mud-accordion-item` each return `summary.errors == 0`, run against
   the BUILT Storybook served on 6099. That script navigates each story and captures

   for this bar and it takes `--port`, so it grades the built artifact rather than a
   dev server. It does not render DOCS pages, so the Accordion docs page's console
   is read once in the browser — the only part of this bar no script covers.

## Self-refute log

**1. Does the fix reuse the defect's own mechanism class?**
Instance. The defect is *a generator silently overwrote output and nobody noticed*.
Phase 3 Step 4 then asks the implementer to look at `git status` and revert the
readmes that are not the Accordion's — a human-judgment step whose failure mode is
exactly "nobody noticed". Paired with its inverse in that step: the forward check
lists what changed, and the closing check `git diff --cached --name-only` must return
only paths under the two accordion directories. The two diverge if a stale readme
rides along and agree if the revert was complete.

**2. Can the rule's letter be met with its intent violated?**
Instance. Bar 2 says the docs page "renders an ArgTypes table ... covering every
member". Hand-authored `argTypes` in the stories meta renders exactly that table and
would pass, while defeating issue #8's intent — generated API docs that track the
source. Conditioned on a fact the artifact must already carry rather than on an
honest label: the bar now requires each rendered row's description to equal the
JSDoc text in `mud-accordion-item.tsx`, and the stories files this plan writes
declare no `description` in any `argTypes` entry. A hand-filled table fails both.

**3. Has every numeric target a denominator, a minimum n, and an instrument outside
what it grades?**
Instance, now closed. "Covering every member" had no denominator. Bar 2 carries one
in a `derived` fence — 9 declared props + 2 events + 4 renderable slots + 2 parts =
17 rows — produced by a regex over the source, minus the two subtractions the bar
states (the default slot's falsy name, and `@Method()` members having no manifest
member at all). The instrument that grades it is different from the one that
produced it: the denominator comes from the `.tsx`, the numerator from the rendered
DOM in Phase 4 Step 3. The `@Method()` exclusion is stated rather than hidden in the
subtraction. The wca mechanism claim in § Context fact 3 is likewise in a `derived`
fence with the command that was actually run, not the reasoning that predicted it —
the first hypothesis there (a line-break in the `@Event` declaration) was refuted by
running it.

**4. Do any two of the artifact's own rules interact into a pass nobody intended?**
Instance. Bar 4 says "spec green, zero new failures", and Phase 1 Step 4 says move
the item's tests verbatim. Satisfy both by failing each one's test in the other's
blind spot: if the new spec file never registers with vitest — wrong directory,
wrong extension, a glob that does not reach it — the run is green, no failure is
new, and the item's 11 tests have silently vanished. Scored as a pair, the fix is a
count rather than a colour: Phase 1 Step 1 records the pre-move test count and Step 8
requires the post-move total to equal it, which neither rule can satisfy alone.
A second pair, checked and clean: Phase 2's `tags: ['!autodocs']` on the item and
Phase 3's regeneration cannot interact, because the tag governs Storybook's story
index and the regeneration governs Stencil's readme output — no artifact is written
by both.

- [ ] **Step 1: Rebuild from a clean manifest and serve**

The `spec` vitest project renders no docs page, so it can be green while this
table is empty — which is exactly how issue #10 shipped. Build and serve:

```bash
WORK="$(git rev-parse --show-toplevel)/.git/accordion-docs-work"; mkdir -p "$WORK"
yarn sp.build 2>&1 | tail -5
npx -y http-server storybook-static -p 6099 --silent &
echo $! > "$WORK/http-server.pid"
```

`-y` because `http-server` is in neither dependency map — without it `npx` stops on
an interactive install prompt. The PID goes to a FILE and not a shell variable:
every fenced block in this plan is its own shell, which is why `WORK` is re-derived
in each one. A `$SERVER` set here would be empty by Step 5, `kill ""` would be a
no-op, and the orphaned server on 6099 would squat the port so the next run silently
reads a stale `storybook-static/` — the exact failure this note exists to prevent.

- [ ] **Step 3: Assert both tables, member by member**

In the page, evaluate against the rendered DOM — a screenshot does not prove a row
exists:

`docblock-argstable` is ONE shared class: `<Controls />` and `<ArgTypes of={ItemStories} />`
both carry it, so a document-wide query returns the container's 8 rows and the item's
17 concatenated, and a membership check over that union proves nothing about which
table a row is on. Index the tables and read each separately:

```js
const tables = [...document.querySelectorAll('.docblock-argstable')];
({
  count: tables.length,                       // must be 2
  container: [...tables[0].querySelectorAll('tbody tr td:first-child')].map(td => td.textContent.trim()),
  item:      [...tables[1].querySelectorAll('tbody tr td:first-child')].map(td => td.textContent.trim()),
});
```

If `count` is not 2, the MDX rendered only one block — stop, the page is wrong before
any row list matters.

Expected, for `mud-accordion-item`, exactly these 17 — the post-Phase-3 state, not
the manifest as it stands today:

- props (9): `open`, `disabled`, `heading`, `supportingText`, `itemId`,
  `appearance`, `breakpoint`, `size`, `iconPosition`
- events (2): `mudToggle`, `mudAccordionItemKey` — the second exists only because
  Phase 3 Step 1 added its `@fires` line, so its absence means that step did not land
- slots (4): `heading`, `supporting`, `icon-start`, `trailing` — NOT the default
  slot, which the extractor drops on its falsy name
- shadow parts (2): `header`, `panel`

And `host` must NOT appear, on either component — that is Phase 2 Step 2/3's
suppression. For `mud-accordion`: `mode`, `appearance`, `size`, `iconPosition`,
`breakpoint`, `items`, `label`, `mudChange`.

Compare that list against the source rather than against this plan:

```bash
grep -n "@Prop\|@Event\|@slot\|@part" src/components/mud-accordion-item/mud-accordion-item.tsx
```

Any declared member missing from the rendered table is a FAIL on bar 2, and so is
a count below the 17 the bar's `derived` fence states.

Then check WHERE the rows came from. A hand-authored `argTypes` table renders the
same names, so the names alone do not distinguish a generated table from a typed
one. Compare the description against the source JSDoc — reading the description
node, not the whole cell: the second `<td>` holds the rendered description AND the
type summary as sibling divs, so its `textContent` is the two concatenated, with
backticks already consumed into `<code>` elements by the markdown renderer.

```js
Array.from(document.querySelectorAll('.docblock-argstable tbody tr'))
  .map(tr => [tr.querySelector('td:first-child')?.textContent.trim(),
              tr.querySelector('td:nth-child(2) > div:first-child')?.textContent.trim()])
  .filter(([n]) => n === 'supportingText' || n === 'panel');
```

Expected: `supportingText` carries "Secondary text shown beneath the heading.
Overridden by the supporting slot." and `panel` carries "The region revealed when
open." — the source JSDoc with its backticks stripped by rendering, which is why the
comparison is against that text and not against the raw `.tsx` line. If
`td:nth-child(2) > div:first-child` comes back empty, fall back to asserting that
the cell's full `textContent` *includes* "Secondary text shown beneath the heading" —
an absent or paraphrased description means the row was not generated from the
manifest.

- [ ] **Step 4: Check the console with the script that actually captures it**

"Zero console errors on every accordion story" must not rest on someone looking, and
`yarn test.storybook` is NOT the mechanism that closes it: `.storybook/vitest.setup.ts`
is an empty `export {}`, nothing under `.storybook/` installs a console trap, and the
per-story test body is a render plus an a11y report. A story that logs an error
passes there. It also grades a different artifact — the project pins
`storybookUrl: 'http://localhost:6007'` with `storybookScript: 'yarn sp.dev'`
(`vitest.config.mts:114-116`), so it auto-spawns a DEV server, while this phase built
and served `storybook-static` on 6099.

The repo already owns the right instrument, and it takes a port:

```bash
node scripts/audit/12-console-errors.mjs mud-accordion --json --port 6099 \
  | python3 -c "import json,sys;d=json.load(sys.stdin);print(d['summary'],[f['code'] for f in d['findings']])"
node scripts/audit/12-console-errors.mjs mud-accordion-item --json --port 6099 \
  | python3 -c "import json,sys;d=json.load(sys.stdin);print(d['summary'],[f['code'] for f in d['findings']])"
```

It navigates each story of the named component and captures `console.error`,
`console.warn` and uncaught `pageerror`. Expected: `errors: 0` from both, against the
BUILT bundle.

It does not render DOCS pages, so the docs page's console is read once in the
browser: `http://localhost:6099/?path=/docs/molecules-accordion--docs`. Expected:
zero errors. That one page is the whole residual of bar 5 no script covers.

Optional, and NOT part of bar 5: `yarn test.storybook` still buys something this PR
has no other coverage for — it renders every story with an a11y check, and this
change adds three stories whose markup has never been through one. Run it only if you
are willing to let it spawn `sp.dev` on 6007, and compare its count against the
baseline Phase 1 Step 1 recorded. A failure there is an a11y finding on new markup,
not a console finding.
