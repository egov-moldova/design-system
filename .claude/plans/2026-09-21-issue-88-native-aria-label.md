# Issue #88 — stop shadowing `HTMLElement.ariaLabel`

## Goal

No `mud-*` component declares a public member that shadows an `HTMLElement` prototype member,
and `@stencil/reserved-member-names` runs as `error`. Consumers keep naming components with the
standard `aria-label` attribute or the native `ariaLabel` property.

## Spec/issue link

https://github.com/egov-moldova/design-system/issues/88

## Re-measured before execution (2026-09-21)

Base: `upstream/main` `ce7dff7` + open PRs #105, #106, #95 merged in (the issue text predates #104,
which removed header/footer). `yarn eslint 'src/components/**/*.tsx' --rule
'{"@stencil/reserved-member-names":"error"}'` → **31** violations: `ariaLabel` in 28 components,
plus `itemId` (accordion-item), `inputmode` (text-input), `ariaValuetext` (numeric-input).

Both the ESLint rule (`@stencil/eslint-plugin` 1.4.0) and the Stencil 4.45 compiler
(`validatePublicName`) compare names lower-cased. Probed in Chromium: `HTMLElement.prototype` has
`ariaLabel`, `inputMode`, `ariaValueText`, and no `itemId`. So only `ariaLabel` is a real
collision; the other three are case-insensitive matches that shadow nothing.

A custom element that does not declare `ariaLabel` reflects `el.ariaLabel = 'x'` to the
`aria-label` attribute natively, and a `MutationObserver` sees that write (Chromium).

## Options

| Option | Cost |
| --- | --- |
| 1. Rename (e.g. `accessibleLabel`) with a deprecation period | New concept; the collision stays until removal, so the rule stays off |
| 2. Read the native `aria-label` attribute, no prop | Type-level break only (`ariaLabel` leaves `components.d.ts` and the React wrapper); runtime keeps both the attribute and the property path |
| 3. Keep the names and document | Collision and 29 compiler warnings stay |

Industry: Ionic (Stencil) reads host `aria-*`, strips it, forwards it inward and keeps it live
with a `MutationObserver` (`core/src/utils/attribute-controller.ts`); Material Web delegates host
ARIA inward (`internal/aria/delegate.ts`); Spectrum Web Components uses a separate `label` prop.
None shadows `ariaLabel`.

## Decision

Option 2 with one shared helper (`src/utils/aria-label.ts`), chosen by the maintainer. The
three false positives keep their names behind a line-level disable that states the measured
reason. `breadcrumb`, `modal`, `pagination` and `date-picker` already read the native attribute
without a prop; they are out of scope here.

## Global constraints

- Branch `fix/issue-88-native-aria-label`; commits stage explicit paths only.
- `src/components.d.ts` and component `readme.md` files are regenerated by the build, never
  hand-edited.
- A component forwards the label to the inner element that owns the role, and strips it from the
  host. A component whose host itself carries the role keeps the attribute on the host
  (`keepOnHost`) and never renders `aria-label` onto `<Host>`.
- Behaviour a component had with the prop (fallback text, visible-label precedence, decorative
  vs announced) stays the same.
