# Claude Code Automation Improvements — Implementation Plan

## Context

The `@age/design-system` repo is a Stencil web-components monorepo with a mature Claude Code setup (5 MCP servers, 4 subagents, 10 slash commands, 15 skills). Project requirements (including accessibility scope) are authored in Figma — the canonical specification for this work is:

- **Figma source of truth:** https://www.figma.com/design/doJ7tDY0PlQ0PqMgbpFVIC/Components?node-id=2753-5965&m=dev (node `2753-5965`). Any change to the skills tree, hooks, or token validator that could affect component a11y must be verified against this node before merge.

Three concrete gaps remain:

1. **No PostToolUse / PreToolUse hooks.** Prettier, ESLint, and Stylelint run only at commit time via Husky. Claude can introduce lint or format errors that go undetected until commit, and can silently waste turns editing generated files (`dist/`, `loader/`, `src/components.d.ts` at 322 KB, `tokens/generated/`, etc.).
2. **Five deprecated skill stubs** consume context-window budget on every session for no benefit. They redirect to `AGENTS.md` / `_agents/*.md`, and the `LOCAL-SETUP.md` cross-IDE-sync language is stale after the recent Windsurf→Claude consolidation (commit `2fafd48`). The sixth deprecated stub (`accessibility-compliance`) is **kept** as a stable pointer to WCAG / ARIA / mobile-a11y guidance because its `references/` folder contains content that may still be consulted; per separate recommendation, deletion is out of scope.
3. **Token validation gaps.** The existing `scripts/tokens-lint.mjs` only enforces naming; `scripts/hardcoded-colors.mjs` catches raw color values. Neither covers reference resolution across tiers, the palette→semantic→component tier-purity rule, DTCG `$value`/`$type` compliance, dark-mode parity, or component-CSS / token-output drift — all of which `tokens/AGENTS.md` defines.

Intended outcome: faster feedback while editing (hooks), a cleaner skill catalog, and a deterministic validator that closes the gap between authoring rules and actual enforcement.

---

## Decisions Locked In

- Hooks live in `.claude/settings.json` (team-shared, checked into git).
- Skill cleanup removes both `.claude/skills/<name>/` **and** `.windsurf/skills/<name>/` for **5** deprecated stubs. `accessibility-compliance` is explicitly **retained** (per separate agent recommendation) — both its `.claude/` and `.windsurf/` copies stay in place, including the `references/` folder.
- Token validator is split: deterministic Node script (`scripts/tokens-validate.mjs`) + orchestrator subagent (`.claude/agents/token-validator.md`).
- WCAG 2.1 AA project requirements (Figma node `2753-5965`) inform the verification step, but no a11y-content migration is required for this plan.

## Work Item 1 — Edit-time hooks

### Files to create

- `.claude/hooks/pre-edit-guard.mjs` — PreToolUse blocker
- `.claude/hooks/post-edit-format.mjs` — PostToolUse formatter/linter dispatcher
- `.claude/settings.json` — wire both hooks into Edit / Write / MultiEdit

### Hook behavior

Both scripts read the Claude Code hook envelope from stdin: `{ tool_name, tool_input: { file_path, ... }, ... }`. They use Node ≥ 22 (already required by `engines.node`).

**`pre-edit-guard.mjs`** — exit 2 (blocking) with a clear stderr message when `file_path` matches any protected glob. Protected paths (derived from `.prettierignore`, `.eslintignore`, `.stylelintignore`, and the Stencil generated files):

```
dist/**                       loader/**              www/**
storybook-static/**           coverage/**            .stencil/**
.wireit/**                    .yarn/cache/**         tokens/generated/**
src/components.d.ts           components/*.d.ts      components/*.js
custom-elements.json          yarn.lock              .storybook/stories/assets/core*.tokens.json
```

The `src/components.d.ts` file is confirmed auto-generated by Stencil (banner at line 1-6). The `components/*.{d.ts,js}` stubs at the repo root are tiny (51-64 byte) re-exports from `dist/`.

**`post-edit-format.mjs`** — dispatches based on `path.extname(file_path)`, only inside the repo source tree (`src/`, `tokens/`, `scripts/`, `.storybook/`, `_agents/`, root config files). Runs commands via `spawnSync('yarn', [...], { shell: true })` so PowerShell + `yarn.cmd` resolve correctly on Windows.

| File pattern | Commands (in order) |
|---|---|
| `**/*.{ts,tsx}` under `src/` | `yarn prettier --write <file>` then `yarn eslint --fix --max-warnings 0 <file>` |
| `**/*.css` under `src/` | `yarn prettier --write <file>` then `yarn stylelint --fix <file>` |
| `tokens/**/*.tokens.json` | `node scripts/tokens-lint.mjs --root tokens/core --no-color --limit 50` (warn-only; do not block) |
| `**/*.{json,md,mjs,js}` outside ignored paths | `yarn prettier --write <file>` only |
| Anything else | no-op |

Exit code: 0 on success; non-zero with stderr message on tool failure (Claude sees the message but is not blocked from continuing). Output kept silent on success to avoid noise.

### Wiring (`.claude/settings.json`)

Merge into the existing file (which currently only has a single permission entry). Final shape:

```jsonc
{
  "permissions": { "allow": ["Bash(node scripts/tokens-lint.mjs --root tokens/core --limit 3)"] },
  "hooks": {
    "PreToolUse":  [{ "matcher": "Edit|Write|MultiEdit", "hooks": [{ "type": "command", "command": "node .claude/hooks/pre-edit-guard.mjs" }] }],
    "PostToolUse": [{ "matcher": "Edit|Write|MultiEdit", "hooks": [{ "type": "command", "command": "node .claude/hooks/post-edit-format.mjs" }] }]
  }
}
```

### Reused utilities

- `yarn prettier`, `yarn eslint`, `yarn stylelint` — already wired through `wireit` (see `package.json` `format` / `lint.js` / `lint.css` / `lint.css.fix` script bodies).
- `scripts/tokens-lint.mjs` — accepts `--root`, `--limit`, `--no-color` per the explored CLI surface.

### Why these are *additions* not duplicates of Husky

Husky's `.husky/pre-commit` runs `yarn typecheck && yarn lint && yarn test` over the whole repo at commit time. The new hooks run *per-file* during Claude's edits, giving feedback ~1-3 s after each tool call instead of after a commit attempt. They are complementary, not redundant.

## Work Item 3 — Token validator (script + subagent)

### File 1: `scripts/tokens-validate.mjs`

A Node ≥ 22 script that loads every `*.tokens.json` under `tokens/core/` and `tokens/core.dark/` and runs the following checks. Exits 0 on clean, 1 on any error, 2 on internal error. Supports `--out <file>` for JSON report and `--no-color`, `--vscode` to match the existing scripts' UX. Reusable from CI and Husky.

| Check | Description | Severity |
|---|---|---|
| **Reference resolution** | Every `"$value": "{path.to.token}"` resolves to an existing token. Detect orphans and typos. | error |
| **Tier purity** | Tier-3 (`tokens/core/components/*.tokens.json`) references must point at semantic tokens (`color.*`, `spacing.*`, `fontFamily.*`, …) — never `palette.*` directly. Per `tokens/AGENTS.md`. | error |
| **Cycle detection** | Reference graph has no cycles. | error |
| **DTCG compliance** | Every leaf token has `$value` and `$type` (never legacy `value`/`type`). Dimensions are explicit strings (`"12px"`, not `12`). `fontWeight` values are numeric. | error |
| **Dark-mode parity** | Every semantic color token in `tokens/core/color.tokens.json` has a matching key in `tokens/core.dark/color.tokens.json`, or is explicitly marked light-only. | warning |
| **Generated CSS drift** | Every token visible in source produces a matching CSS variable in `tokens/generated/core.tokens.css`. (Implementation: re-run Style Dictionary to a temp dir, diff against committed output. Skip if `--no-build` flag.) | warning |
| **Component-CSS coverage** | For each `tokens/core/components/<name>.tokens.json`, find `src/components/cor-<name>/cor-<name>.css` and check that every `--<name>-*` CSS variable referenced has a token definition, and (warn-only) every defined token is used. | warning |

The script imports `style-dictionary` (already a devDependency at version 4.4.0) to resolve references using the same algorithm Style Dictionary uses internally, avoiding parser drift.

### File 2: `.claude/agents/token-validator.md`

A subagent that orchestrates and explains. Definition outline:

```yaml
---
name: token-validator
description: Validates the 3-tier design-token hierarchy. Runs tokens-lint, hardcoded-colors, and tokens-validate, then summarizes findings and proposes fixes with file:line references. Read-only by default.
tools: Read, Grep, Glob, Bash
---
```

Body covers:
- Run order: `yarn lint.tokens` → `yarn lint.colors` → `node scripts/tokens-validate.mjs --out /tmp/tokens-validate.json`.
- Parse the JSON output, group findings by severity and tier, surface the 5 most impactful errors first.
- For each error, offer a concrete fix (e.g., "change `{palette.gray.250}` to `{color.border.default}` on `tokens/core/components/input.tokens.json:42`").
- For warnings (dark-mode parity, CSS drift), explain *why* before suggesting a fix.
- Do NOT auto-apply fixes. The subagent is invoked manually by the user via the Task tool when they want a review.

### File 3: `package.json` script (optional but recommended)

Add `"tokens.validate": "node scripts/tokens-validate.mjs"` to `scripts` and a matching wireit entry that depends on it from `lint`. This makes the validator part of the Husky pre-commit pipeline (`.husky/pre-commit` already runs `yarn lint`).

### Why split (script + agent)

- The deterministic graph checks (reference resolution, cycles, tier purity, DTCG compliance) are O(n) over JSON files. Doing them via LLM reasoning over 60+ component-token files is slow, expensive, and non-deterministic.
- The script alone is reusable from CI / Husky / VSCode tasks.
- The subagent adds the *judgment* layer (which errors matter most, how to phrase the fix, what to do about borderline warnings) without re-inventing the parsing.
